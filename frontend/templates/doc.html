SECTION 01

Executive Overview

In multi-agent collaborative workflows and long-running software engineering sessions, agents accumulate conversational transcripts that quickly exceed 50,000 to 120,000 tokens. Traditional agent frameworks naively dump the entire conversational history into every single LLM prompt invocation.

This results in quadratic GPU attention overhead, burns rate limits, incurs severe prefill latencies (12s–30s+), and risks memory degradation. BFSContext replaces naive history concatenation with deterministic AST Slicing and Tiered Memory Direct Hash Indexing.

SECTION 03

Tiered Memory Architecture (L1 / L2 / L3)

To maintain extreme throughput without consuming host RAM, BFSContext organizes context memory into three deterministic tiers:

Memory Tier Hardware Backing Capacity / Footprint Lookup Latency Eviction & Persistence Policy
L1 Cache Host RAM (Python Micro-LRU) Strictly bounded < 10 KB (50 active symbols) 0.001 ms Least-Recently-Used (LRU). Discards to L2 upon capacity limit.
L2 Cache NVMe SSD (SQLite WAL) Unlimited persistent symbol records 0.066 ms - 0.15 ms WAL (Write-Ahead Log) mode. Multi-process concurrent read lock.
L3 Cold Store Git Object Database & AST Slicer Full Repository History (121,428 tokens) 1.5 ms - 5.0 ms Source of truth. Auto-rebuilds L1/L2 on cache misses or corruption.

SECTION 04

Direct Hash Indexing: O(1) Amortized Lookups

Rather than walking polynomial Abstract Syntax Tree (AST) dependency graphs on every user query, BFSContext computes a deterministic SHA-256 compound hash: 

hash_key = SHA256( f"{file_path}:{symbol_name}:{commit_sha}" )
Example:
file_path  = "src/core/stream/RingBuffer.ts"
symbol     = "RingBuffer"
commit_sha = "fe40af24"
hash_key   = "a702ba97307ceae4daa1cf68510c941cc2d3c14894701a16ebc2732f11335732"

Because lookups rely on primary key B-Tree indexes on SSD, retrieval time is mathematically $O(1)$ amortized (0.066ms), regardless of whether the codebase has 10 files or 100,000 files.

SECTION 05

End-to-End Live Workflow (Task 6 Alignment)

The system implements a rigorous 4-step pipeline: Input → Processing → Decision → Output / Action.

Step 1: Input — User enters task query (e.g. "Write high-performance circular buffer tests"). Full conversational session database holds 121,428 historical tokens in SQLite.
Step 2: Processing — Direct Hash Indexer parses the query symbols, computes SHA-256 keys, and queries L1 RAM / L2 SSD caches in 0.066ms.
Step 3: Decision — Cache controller checks for cache hit. If present, it packages the exact target contract into a ~247-token Context Capsule. If missing, it triggers an L3 AST slice and updates the SSD cache.
Step 4: Output / Action — Dispatches dual streams: Baseline undergoes prefill delay; BFSContext streams immediately in ~1.7s. All telemetry is logged to persistent JSON storage.
